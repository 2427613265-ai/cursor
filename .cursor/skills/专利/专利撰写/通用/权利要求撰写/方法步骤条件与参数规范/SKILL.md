# 方法步骤条件与参数规范

原 `条件判断语句规范`、`预设值与参数来源检查` 已收束于此。**规则全文保留**。主要适用于方法/算法权要；结构案若有预设参数，第二节同样适用。

条件判断的**判断主体**须明确，见 `权利要求表达清楚性规范` 第一节。参数**含义**是否说清见 `权利要求命名细则` 第五节；本节只管**来源**。

## 分节何时用

| 时机 | 节 |
|------|----|
| 出现条件分支 | 一、判断句式 |
| 出现阈值/预设/运行参数 | 二、参数来源 |

## 一、条件判断句式（原「条件判断语句规范」）

### 核心规则

在撰写方法类或算法类权利要求时，涉及条件判断的步骤必须使用规范的判断语句格式。

#### 基本格式

**单一条件判断（带else分支）：**
```
判断是否满足[条件描述]，若是，则[执行操作A]；若否，则[执行操作B]
```

**单一条件判断（仅true分支）：**
```
判断是否满足[条件描述]，若是，则[执行操作A]
```

#### 禁止使用的表达方式

❌ **错误示范：**
- "如果满足条件A，那么执行操作B"
- "当条件A成立时，执行操作B"
- "在条件A的情况下，进行操作B"
- "检测是否满足条件A，是的话执行操作B"
- "如检测到条件A，则执行操作B"

✅ **正确表达：**
- "判断是否满足条件A，若是，则执行操作B"

---

### 详细规范

#### 1. 基本条件判断

##### 仅有 true 分支

**格式：**
```
判断是否满足[条件]，若是，则[操作]
```

**示例：**
```
判断所述温度值是否大于预设阈值，若是，则触发报警信号
```

##### 包含 true 和 false 分支

**格式：**
```
判断是否满足[条件]，若是，则[操作A]；若否，则[操作B]
```

**示例：**
```
判断所述用户权限级别是否为管理员权限，若是，则允许访问；若否，则拒绝访问并记录日志
```

#### 2. 多条件判断

##### 与关系（AND）

**格式：**
```
判断是否同时满足[条件1]和[条件2]，若是，则[操作]
```

或更明确地：
```
判断是否满足[条件1]且满足[条件2]，若是，则[操作]
```

**示例：**
```
判断是否同时满足所述温度值大于30℃和所述湿度值小于50%，若是，则启动降温装置
```

```
判断是否满足所述用户已登录且所述会话未超时，若是，则允许继续操作；若否，则跳转至登录页面
```

##### 或关系（OR）

**格式：**
```
判断是否满足[条件1]或[条件2]，若是，则[操作]
```

**示例：**
```
判断是否满足所述电量低于10%或所述设备温度高于安全阈值，若是，则进入保护模式
```

##### 复杂组合条件

对于复杂的多条件组合，保持"判断是否满足..."的句式，条件部分可以适当使用括号和连接词：

**示例：**
```
判断是否满足（所述用户权限为高级权限或所述用户属于管理员组）且所述操作类型为敏感操作，若是，则要求二次验证；若否，则直接执行
```

#### 3. 嵌套条件判断

当需要表达嵌套的条件判断时，应拆分为多个独立步骤，每个步骤保持独立的判断语句格式。

❌ **错误示范（单步骤内嵌套）：**
```
S3：判断是否满足条件A，若是，则判断是否满足条件B，若条件B也满足则执行操作C，否则执行操作D
```

✅ **正确示范（拆分为多个步骤）：**
```
S3：判断是否满足条件A，若是，则进入步骤S4；若否，则进入步骤S6；
S4：判断是否满足条件B，若是，则执行操作C；若否，则执行操作D；
S5：...
S6：...
```

---

### 检查清单

在撰写或审核涉及条件判断的权利要求时，逐项检查：

- [ ] 所有条件判断是否都使用"判断是否满足..."开头
- [ ] true分支是否都使用"若是，则..."
- [ ] false分支（如有）是否都使用"若否，则..."
- [ ] 是否存在"如果...那么..."、"当...时..."等口语化表达
- [ ] 多条件判断的逻辑关系（与/或）是否表达清楚
- [ ] 嵌套判断是否已拆分为独立步骤
- [ ] 条件描述是否明确、可验证（避免"合适"、"适当"等模糊词）

---

### 正确示例汇总

#### 示例1：简单判断（仅true分支）
```
S3：判断所述检测值是否超过所述预设上限，若是，则生成警告信息；
```

#### 示例2：完整判断（true和false分支）
```
S4：判断所述用户输入是否为有效格式，若是，则进入下一步处理；若否，则返回错误提示信息；
```

#### 示例3：与条件
```
S5：判断是否同时满足所述距离小于安全距离和所述速度大于预设速度，若是，则触发制动系统；
```

#### 示例4：或条件
```
S6：判断是否满足所述电池电量低于阈值或所述设备进入低功耗模式，若是，则关闭非必要功能模块；
```

#### 示例5：复杂条件组合
```
S7：判断是否满足（所述时间段为工作时间且所述用户已认证）或所述请求标记为紧急请求，若是，则立即处理请求；若否，则将请求加入待处理队列；
```

---

### 错误示例与修正

#### 错误1：使用"如果"句式
❌ **错误：**
```
S3：如果检测值超过预设上限，那么生成警告信息；
```

✅ **修正：**
```
S3：判断所述检测值是否超过所述预设上限，若是，则生成警告信息；
```

#### 错误2：使用"当...时"句式
❌ **错误：**
```
S4：当用户权限为管理员时，允许执行删除操作；
```

✅ **修正：**
```
S4：判断所述用户权限是否为管理员权限，若是，则允许执行删除操作；
```

#### 错误3：口语化表达
❌ **错误：**
```
S5：检查温度是不是太高了，是的话就打开风扇；
```

✅ **修正：**
```
S5：判断所述温度值是否高于安全阈值，若是，则启动散热风扇；
```

#### 错误4：混用表达方式
❌ **错误：**
```
S6：判断是否满足条件A，如果是，则执行操作B；
```

✅ **修正：**
```
S6：判断是否满足条件A，若是，则执行操作B；
```

#### 错误5：条件和操作混在一起
❌ **错误：**
```
S7：检测到异常时发送通知；
```

✅ **修正：**
```
S7：判断是否检测到异常，若是，则发送通知；
```

---

### 注意事项

1. **"判断"是必需的开头词**：所有涉及条件判断的步骤都必须以"判断是否满足..."或"判断是否..."开头。

2. **"若是"和"若否"是固定搭配**：不要使用"如果是"、"要是"、"假如"、"倘若"等其他词汇。

3. **条件必须可验证**：条件描述应当是明确、客观、可验证的，避免使用"合适"、"适当"、"较好"等主观或模糊的表达。

4. **保持步骤独立**：每个步骤应该是独立、完整的操作单元，复杂的嵌套判断应拆分为多个步骤。

5. **适用范围**：本规范主要适用于方法类和算法类权利要求，结构类权利要求一般不涉及条件判断。

---

### 与其他规范的配合

本规范应与以下技能配合使用：
- `权利要求表达清楚性规范第三节` - 权利要求的清楚性与逻辑检查
- `权利要求形式与依附规范第一节` - 权利要求的形式合规检查
- `独立权利要求必要技术特征检查` - 必要技术特征检查

在撰写完成后，应先应用本规范检查判断语句格式，再应用上述技能进行全面质检。

## 二、预设值与参数来源（原「预设值与参数来源检查」）

### 核心思想：把自己当作一个只会照做的机器人

权利要求是一份要交给"机器人"逐字执行的技术方案说明书。这个机器人**没有任何常识补全能力**，它只会严格按照权利要求写出来的文字，一步一步执行——权利要求没写的数据，它就拿不到；权利要求没交代来源的参数，它就无从获得。

因此，权利要求里每出现一个**预设值、阈值、具体参数、系数、比例、目标值、基准值、参考数据**等，撰写者都要停下来，站在机器人的立场连问三个问题：

1. **这个数据是权利要求里已经给定 / 已知的吗？**（比如是权利要求前文已经设定的、或本领域公认的固定常量）
2. **如果不是给定的，我（机器人）能直接获得它吗？**（比如通过一个已经写明的传感器、已经写明的计算步骤直接得到）
3. **如果两者都不成立**——即这个数据既不是已知的、机器人也没法凭现有步骤拿到——那么权利要求**必须先补上"获取 / 测量 / 采集 / 计算 / 设定 / 读取"这个参数的步骤**，然后才能在后续步骤里使用它。

**一句话规则：任何被"使用"的数据，在权利要求里必须先有明确的"来源"（给定、获取或算得），不能凭空出现、直接就用。**

### 三种数据来源，各自的合规写法

| 数据类型 | 是否需要补充获取步骤 | 说明 |
|----------|---------------------|------|
| **已给定/预先设定的值**（如"预设阈值T"） | 需要交代它是"预先设定的"，并尽量说明设定依据/范围 | 允许作为已知量直接使用，但要让机器人知道"这是一个预设量"，而不是需要它现算的量 |
| **本领域公认的固定常量**（如重力加速度、水的密度） | 不需要 | 机器人可视为已知，属于公知常识 |
| **依赖运行时才能确定的量**（如"实时采集的温度""当前转速""检测到的距离"） | **必须**先写明获取/测量/计算步骤 | 机器人执行前并不掌握这个数据，必须先有一步把它拿到 |

### 判断方法（撰写时随手自查 / 质检时逐条核对）

对权利要求中每一个数值、参数、变量，执行以下流程：

```
发现一个参数 X
  → 问1：X 是权利要求前文已经"预先设定"或"给定"的吗？
        是 → 检查是否已明确写出"预设/给定"字样，合规；
        否 → 进入问2
  → 问2：X 是本领域公认的固定常量（公知常识）吗？
        是 → 可直接使用，合规；
        否 → 进入问3
  → 问3：在使用 X 的这一步之前，权利要求里有没有一步明确"获取/测量/采集/计算/读取"了 X？
        有 → 合规；
        没有 → 缺陷：X 凭空出现、来源缺失，必须补上获取 X 的前置步骤，或说明它是预设值。
```

### 正确 / 错误示范

#### 示范一：实时参数缺少获取步骤

```
错误：
一种温控方法，其特征在于，包括：
  当温度超过预设阈值时，启动制冷模块。
```

机器人视角的问题：**"温度"这个数据从哪来？** 权利要求从头到尾没有一步告诉机器人去"测量温度"，机器人手上根本没有温度值，无法执行"当温度超过预设阈值时"这个判断。（另外"预设阈值"虽然点明了是预设的，但如果全文没有任何设定/取值说明，也偏弱，见示范二。）

```
正确：
一种温控方法，其特征在于，包括：
  通过温度传感器实时采集被控空间的温度；
  判断所述温度是否超过预设阈值，若是，则启动制冷模块。
```

补上了"采集温度"这一步，机器人才拿得到"温度"，后面的判断才可执行。

#### 示范二：预设值来源不清

```
偏弱：
  ……当偏差大于系数K时，触发校正。
```

"系数K"是什么？机器人不知道它的值，也不知道去哪拿。

```
正确（作为预设值）：
  预先设定校正系数K；
  ……当所述偏差大于所述系数K时，触发校正。
```
或（作为算得的值）：
```
  根据所述历史数据计算得到校正系数K；
  ……当所述偏差大于所述系数K时，触发校正。
```

#### 示范三：算法类中间量凭空出现

```
错误：
  根据置信度对候选结果排序，输出置信度最高的结果。
```

机器人视角：**"置信度"是怎么来的？** 没有任何一步计算出各候选结果的置信度。

```
正确：
  对每个候选结果，计算其对应的置信度；
  根据所述置信度对所述候选结果排序，输出置信度最高的结果。
```

### 与其他规范的关系

- 本节是 `权利要求表达清楚性规范第三节` 中"孤岛特征""突然出现的术语"两条规则在**数据/参数**维度上的具体化和强化：孤岛特征关注的是"特征有没有后续呼应"，本节关注的是"数据有没有前置来源"，方向相反、互补。
- 方法类/算法类权利要求中，参数获取步骤往往还涉及条件判断，配合 `本细则第一节（判断句式）` 一起检查。
- 若参数本身是非公知的自定义名词（如"调节比""置信度"），其**含义**是否在权要内说清由 `权利要求命名细则第五节` 负责（优先前置白话，其中兜底）；本节负责的是它的**来源**是否交代。两者都要过一遍。
- 主要适用于**方法类、算法类**权利要求（步骤按时间顺序执行，"先获取后使用"的次序要求最强）；结构类权利要求若涉及"预设参数/设定值"，同样要交代该参数是预设的还是可调的。

### 检查清单

- [ ] 权利要求中每一个数值、阈值、参数、系数、比例、目标值，是否都能回答"它从哪来"？
- [ ] 依赖运行时才能确定的量（温度、转速、距离、置信度等），在被使用之前，是否有明确的获取/测量/计算步骤？
- [ ] 预设值/给定值是否已明确写出"预设""预先设定""给定"等字样，让机器人知道无需现算？
- [ ] 是否存在既非公知常量、又没有获取步骤、却被直接拿来判断或计算的"凭空参数"？
- [ ] 步骤顺序是否满足"先获取、后使用"——获取参数的步骤是否排在使用该参数的步骤之前？

### 应用范围

撰写权利要求时应边写边用"机器人视角"自查每一个参数的来源；对已撰写完成的权利要求书做质检时，本节作为 `权利要求质检总控` → `权利要求书质检` 的专项检查项（尤其针对方法类/算法类案件）纳入使用。
