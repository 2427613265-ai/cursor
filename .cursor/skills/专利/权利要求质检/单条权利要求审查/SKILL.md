# 单条权利要求审查（具体质检 skill）

当用户提到检查、审阅或修改**某一条**权利要求（如"权1""权2""权利要求3"等）时，由 `权利要求质检总控` 分流至本 skill，按以下三个维度逐一检查，逐条给出具体问题和修改建议，而不是笼统评价。若某维度未发现问题，也要明确指出"该维度未发现问题"。

**调用关系（硬性）：** 本 skill **不是**质检总入口，也**不是**权要质检二级入口。用户说「质检／审核／检查」时：**禁止直接触发本 skill**；必须先 `质检总控` → `权利要求质检总控`；二级总控判定为单条后再调用本 skill。若误被直触，应立即改走上述链路，不在本 skill 内独自收口。

**与整份质检的分工**：本 skill 聚焦**单条权利要求的实质审查**（逻辑、表达、格式）。涉及整份权利要求书的编号核对、引用结构布局、形式合规等系统性检查时，应改由 `权利要求质检总控` 走整份链路（`权利要求形式合规性规范` → `权利要求引用结构检查` → `权利要求书质检`），避免与本 skill 重复展开相同检查项。

## 1. 逻辑完善性与保护范围

- 引用关系是否正确：从权引用的权利要求号是否存在、主题类型是否一致（如方法权利要求不应引用装置权利要求）。
- **术语出处／依附编号（从权）：** 本条若含「所述××」，按需 Read 并执行 `权利要求依附编号与术语出处规范`（列词 → 全文溯源 → 引用链覆盖；失败给 A/B/C）。单条审查只核本条；若改引用／重排可能牵动全文，末尾提醒升格整份链路。
- 是否遗漏解决技术问题所必需的技术特征，独权是否因此保护范围不稳固。可结合 `独立权利要求必要技术特征检查` 核对。
- 独权概括是否过宽（可能缺乏新颖性/创造性支持）或过窄（保护范围不必要地受限）；含方位/场景钉死语时按需加载 `方位与场景限定上位规范`。
- 从权是否层层递进、逐步限缩，是否存在从权与独权特征矛盾、重复或从权未实际缩小保护范围的情况。
- 格式类引用问题（引用方向、多项从权择一引用等）以 `权利要求形式合规性规范` 为准，本维度只关注该条权利要求层面的逻辑后果。

## 2. 表达清楚性

以 `权利要求清楚性与逻辑一致性规范` 为总则；指代、主谓、方位词问题按需参照 `权利要求指代与参照清晰性规范` 和 `权利要求主谓宾结构规范`。重点包括：

- 用词是否精确、无歧义，是否存在模糊限定词（如"较大""适当""大约"）
- 同一技术特征命名和表述是否前后一致
- "所述"使用是否规范；从权「所述××」的先行基础是否落在引用链上（与维度1挂接的 `权利要求依附编号与术语出处规范` 同一核对，此处不重写算法）
- 句式是否冗长、是否存在多重修饰导致的指代不清
- 功能性限定是否有说明书具体实施方式的支持

## 3. 撰写规范与格式

以 `权利要求形式合规性规范` 为准，本维度补充单条层面的观察：

- 独权是否为"一种……"等规范句式，是否包含前序部分和特征部分（以"其特征在于"分隔）
- 从权引用格式是否规范
- 主题名称是否与说明书、摘要对应
- 开放式（"包括"）与封闭式（"由……组成"）过渡词是否恰当
- 结构类从权引入新部件时，是否遵循 `结构类权利要求撰写`（先总述同级部件、后展开；子部件不得与母件并列写进同一句「还包括」）
- 出现交底口语名/非自明名称时是否遵循 `交底口语名改写为自明结构名规范`（先判断能否改成更自明结构名，再决定是否用“其中”）
- 方法类/算法类条件判断步骤是否遵循 `条件判断语句规范`
- 出现方位/场景限定语时是否遵循 `方位与场景限定上位规范`（观察方位默认「一侧」；上下游/功能侧慎改；场景语能放宽则放宽）
- 从权「所述」术语出处问题以 `权利要求依附编号与术语出处规范` 为准（与形式合规的「引用号须小于本条」区分）

## 输出格式

按维度分点列出问题，每条说明：具体位置/特征 → 存在的问题 → 修改建议。全部检查完后，如有必要可给出优先级最高的 1-3 条改进建议汇总。

若审查中发现编号或引用关系可能影响全文，在末尾提醒用户按 `权利要求质检总控` 走整份权要链路复核。
