# 权利要求书质检（具体质检 skill）

本 skill 用于**整体复核**已经撰写完成的权利要求书的**实质与布局**。

**调用关系（硬性）：** 由 `权利要求质检总控` 在整份权要链路中、于形式合规与引用结构检查之后调用。本 skill **不是**质检总入口，也**不是**权要质检二级入口。用户说「质检／审核／检查」时：**禁止直接触发本 skill**；必须先 `质检总控` → `权利要求质检总控`，再由二级总控编排调用本 skill。若误被直触，应立即改走上述链路，不在本 skill 内独自收口。

## 与总控、单条审查的分工

| 场景 | 使用哪个 skill |
|------|---------------|
| 用户说「质检」「审核」且对象待判定 | `质检总控`（顶层）→ 再分流二级总控 |
| 判定为**整份**权利要求书 | `权利要求质检总控` → 本 skill + 形式合规 / 引用结构 |
| 用户指定检查**某一条**权利要求 | `权利要求质检总控` → `单条权利要求审查` |
| 单条修改后影响全文编号或引用 | 先 `单条权利要求审查`；再由 `权利要求质检总控` 升格跑整份链路（含本 skill） |

## 标准质检流程与 skill 读取分级

整份链路的前两步由 `权利要求质检总控` 编排；进入本 skill 时默认**形式合规与引用结构已完成或正由该二级总控并行调度**。本 skill 负责实质四维度，并按需加载撰写规范。

```
权利要求质检总控编排（进入本 skill 前/同时）：
  1. 权利要求形式与依附规范           → 形式合规硬伤
  2. 权利要求引用结构检查             → 平行/串联引用结构

本 skill（实质与布局）：
  3. 维度一至四（其中维度二第1点依附编号 = 执行 `权利要求形式与依附规范`）
  4. 按需深入加载下列规范
```

**必读（进入维度二第1点时）：**

- `权利要求形式与依附规范`（算法唯一出处；本 skill 不重写）

**按需深入：**

- 结构类案件或有装置/部件类从权  
  → `结构类权利要求撰写`、`功能性限定使用边界规范`
- 方法类/算法类案件或含条件判断、预设值/阈值/参数  
  → `方法步骤条件与参数规范`
- 口语名、非公知概念、方位/场景钉死语  
  → `权利要求命名细则`
- 维度三发现指代、主谓或方位词问题  
  → `权利要求表达清楚性规范`
- 独权范围需逐项核对某特征是否必要时  
  → `独立权利要求必要技术特征检查`

**执行顺序（与总控一致）**：先形式硬伤 → 再引用结构 → 最后按下面四个维度做实质审查。**优先输出可机械核对的硬伤**，再讨论范围/创造性/梯度等需专业判断的问题。

## 维度一：独立权利要求——保护范围与创造性的平衡

1. **必要技术特征是否齐全**：独权是否包含了解决其声称的技术问题所必需的全部技术特征？少了任何一个，方案就不完整、可能得不到说明书支持。
2. **有没有可以删掉但不影响创造性的多余限定**：独权里每一个技术特征，如果删掉后方案仍然新颖、非显而易见、仍能解决背景技术指出的问题，这个特征就应该降级到从权，不要留在独权里不必要地缩小保护范围。可结合 `独立权利要求必要技术特征检查` 逐项核对。
3. **核心区别特征是否真的能支撑创造性**：与背景技术提到的最接近现有技术相比，独权的区别技术特征是不是本领域技术人员容易想到的常规变型？这个区别特征带来的效果是不是真正非显而易见？
4. **保护范围有没有被不必要的具体数值/具体实现方式绑死**：独权里如果出现了具体角度数值、具体一种机构（比如限位槽+限位销这种具体结构），要考虑这些是否该降级到从权，让独权保持更概括的表达。
5. **独权里保留的功能性限定/效果陈述，是否构成了不必要的隐含限定**：如果独权里写了"从而实现XX效果"，理论上会被解释为一个隐含的限定条件（即必须真正产生这个效果才落入保护范围），如果这是撰写者主动的取舍要如实告知，不是撰写者本意就要建议删除。

## 维度二：从属权利要求——依附关系与梯度防御布局

1. **依附编号是否正确——逐条机械核对**：必读并执行 `权利要求形式与依附规范`（列词 → 全文溯源首次出现权号 → 引用链覆盖判定 → 失败给 A/B/C 处置）。**本维度不重写该算法**；质检输出「依附编号错误」栏按该规范的全文核对表／逐条意见格式填写。这是最容易在插入/删除/重排权利要求后出错、也是最容易被审查员一眼挑出来的问题，每次调整编号后必须按该规范全篇重核，不能只抽查改过的那几条。
2. **引用结构是否合理——平行/串联选择**：按 `权利要求引用结构检查` 检查：相互独立的改进点是否平行引用同一基础权利要求；存在技术依赖的改进点是否正确串联引用；组合改进是否使用"或/任一项"式多项引用。不必要的串联引用会让读者误以为存在技术依赖，也会限制从权的独立主张空间。
3. **梯度是否合理——由概括到具体，由结构到数值**：好的布局应该是"先用一条从权概括性地限定技术手段 → 再用下一条限定其具体结构 → 再用更下一条限定具体数值/档位/锁定方式"。检查是否存在"一步到位塞入所有细节"（层次不够）或者"该合并的却拆得太细"（浪费权利要求数量）。如果几个并列分支的精细程度不对称（比如一个分支拆了三层、另一个分支只有两层），要指出来，由用户决定是否要为了对称性再调整。
4. **从权分支之间有没有实质重复**：检查是否存在两条从权本质上用的是同一种技术手段（哪怕依附对象、措辞不同），如果一条已经隐含覆盖了另一条的保护范围，后者对创造性没有增量贡献，应删除或改成确实不同的技术方案。
5. **并列的互斥实施例分支有没有交叉污染**：比如两种互斥的替代实施例（分支A、分支B）应该各自独立依附同一个上位权利要求，检查有没有从权错误地跨分支引用了另一分支才有的术语。

## 维度三：逻辑完善性与清楚性

以 `权利要求表达清楚性规范` 为总则（该 skill 须先 Read `清楚性与逻辑一致性共用内核`）；指代、主谓或方位词问题在该规范第一、二节深挖。检查项包括：

- 孤岛特征（仅出现一次、前后都未呼应的特征，公知术语/暗含于后续操作的特征除外）
- 突然出现且不是客观清楚物理量的人为定义术语，是否已在权利要求内部说清；**是否优先改自明名或在名称出现前白话描述，而非默认堆「其中」**（详见 `权利要求命名细则`）
- 技术概念模糊或含义不确定的用语（"大致""适当"等）
- 权利要求是否存在歧义或可以构造出反例
- 描述是否清楚、简洁
- 是否违背物理/数学常识，或前后（含从权与其依附对象之间）逻辑矛盾
- **参数来源（机器人视角）**：每个预设值/阈值/参数/系数在被使用前是否都有明确来源（给定、公知常量或已写明获取步骤），有无凭空出现、直接就用的"无源参数"——详见 `方法步骤条件与参数规范`
- 术语前后一致：同一个技术特征自始至终只用同一个名称指代
- 引用编号与术语来源要对应（与维度二第1点同一事：执行 `权利要求形式与依附规范`）
- 主谓宾结构：每个动作是否有明确执行者，避免因省略主语导致指代不明
- 指代词清晰性：优先使用"所述+完整名称"；存在多个同类对象时必须消歧
- 方位词参照物：周向/轴向/径向、平行/垂直等是否明确了参照物

## 维度四：表达清楚性（按案件类型按需检查）

- 结构类案件：`结构类权利要求撰写`——是否先总述部件、后展开结构
- 结构类案件：`功能性限定使用边界规范`——功能性限定/技术效果表述是否恰当
- 方法类/算法类案件：`方法步骤条件与参数规范`——条件句式与参数来源
- 口语名、非公知概念、方位/场景钉死语：`权利要求命名细则`

## 输出格式

质检结果按以下顺序输出（与 `权利要求质检总控` 收口一致）：

1. 形式合规性硬伤（`权利要求形式与依附规范`）
2. 引用结构问题（`权利要求引用结构检查`：不必要的串联/错误的平行引用等）
3. 依附编号错误（执行 `权利要求形式与依附规范`；逐条列出"第几条 → 问题词 → 首次出现权号 → 建议 A/B/C"）
4. 实质重复问题
5. 独权范围与创造性观察
6. 从权梯度布局观察
7. 表达清楚性核对（如有遗漏）
